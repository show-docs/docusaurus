## 端到端（Playwright + BDD）

`e2e/` 是另一层：跑的是**构建产物**（`pnpm build` 之后由 `docusaurus serve` 起在
`http://localhost:3021`），在真浏览器里点开每个主题的示例页。

```bash
pnpm test:e2e                         # 依次跑：pnpm build → bddgen → playwright test
pnpm exec playwright install chromium # 只做一次：浏览器不在依赖里，由 Playwright 自己下
```

用例写成 Gherkin：`features/*.feature` 里是 Given/When/Then 的句子（关键词英文，句子中文），
`steps/*.steps.mts` 里是这些句子的实现。`bddgen` 把两者生成到仓库根的 `.features-gen/`，
Playwright 跑的就是那份产物 —— 它是生成物，不进 git，也别手改。
写成句子不是为了文档好看：`.feature` 里有句子却没有对应实现时，`bddgen` 在生成阶段就报错，
漏实现不会等到跑到一半才暴露。**同一句话在两个 `steps/*.steps.mts` 里各写一遍也是错误**
（`Multiple definitions matched scenario step`，生成阶段就停）—— 几条层要共用一句就把它挪进
`common.steps.mts`，让实现只有一份；各层专属的句子留在各层，名字撞了要改句子，不是改实现。

为什么要这一层：`pnpm test` 与 `pnpm verify:chain` 读的都是**产物文本**（层栈标记、HTML 里有没有
某个标签）。有两类失败只有浏览器能看见 —— 一是运行期才抛的错（例如 `@stoplight/elements` 那份
浏览器 bundle 引用裸的 `process`，构建全绿、页面空白），二是「标签在 HTML 里，但 React 没把它
渲染出来」。第一条靠 `watchPageErrors()`（收 `pageerror`）拦，第二条靠断言元素真的可见拦。

这套用例抓到过三处真缺陷，都是「构建全绿、类型全绿、只有开页面才看得见」的那类：
`theme-iframe` 那层静默不渲染（官方 `DocItem` 不读 `props.children`，iframe 被当成 children 塞进去，
产物里 `iframe` 标签数为 0）；`theme-redoc` 的 `basePath` 用默认值时 Redoc 一声不吭地渲染**它自己那份 404**
（左栏、样式全在，正文区写着 No page at this address，控制台干净）；还有一处是**只在跑用例时现身**的
时序缺陷 —— 框里那句「我起来了」可能先于外层的监听器发出（命中缓存时框里那份文档跑得比外层的水合
还快），于是深链与亮暗模式都收不到。外层也主动推一次之后才不丢；为什么单跑绿、整套跑也绿、只有开着
trace 才红，记在 [`packages/theme-component-page/docs/iframe-protocol.md`](../packages/theme-component-page/docs/iframe-protocol.md)
（那条通道现在 redoc、stoplight、scalar 三条层共用）。三层的用法与限制分别记在
[`packages/theme-redoc/README.md`](../packages/theme-redoc/README.md)、
[`packages/theme-stoplight/README.md`](../packages/theme-stoplight/README.md)、
[`packages/theme-scalar/README.md`](../packages/theme-scalar/README.md)，
实现细节与实测记录在各包同目录的 `docs/internals.md`，通道本身在
[`packages/theme-component-page/docs/iframe-protocol.md`](../packages/theme-component-page/docs/iframe-protocol.md)。

## 覆盖率

CI 把全量覆盖率红线钉在 **100%**，增量同样 100 —— 新增代码必须自带用例。

量哪几份写在 `vitest.config.mts` 的 `coverage.include`：**所有包的构建期代码** —— 每个包的 `src/`（配置期接线、webpack 规则、loader 判据、纯逻辑），加上 `packages/theme-component-page/lib/`（配置期与浏览器期共用的那条命中判据与那张规则表、同源框的消息形状与两侧的同步 hook、按需装载渲染器那层壳、框内那份文档的地址算法、三条视图层共用那份外壳、静态样式表的分流）与 `packages/theme-iframe/lib/`（`iframe:` 那一格嵌外站时地址怎么算）。这一层实测 47 份文件，行 / 语句 / 函数 / 分支四项全 100。

构建期那几处判据各住在哪里：

- `test/theme-git-badge.test.mts` —— 徽标种类、注入、地盘、git 那一侧与接线（`themes/theme-git-badge/src/`）。
- `test/theme-diff.test.mts` —— `diff:` 那把键怎么读、git 里那一次改动怎么落成一份数据（`packages/theme-diff/src/`）。
- `test/theme-erd.test.mts` —— 一份 `.dbml` 编成 MDX、配置期那份 `exports` 清单（`packages/theme-erd/src/`）。
- `test/theme-markmap.test.mts` —— 一份 md 落成导图数据、loader 在四种情形下追加什么（`packages/theme-markmap/src/`）。
- `test/package-entries.test.mts` —— 每个包入口交出的那几格：名字、层目录、客户端模块、
  webpack 规则，以及前置条件不满足时点名到谁。

红线之外的是**浏览器侧那层**（各包 `theme/` 与 `components/` 下的视图，以及站点的 `src/theme/` 与
`src/components/`）—— 那些只有开页面才看得见，
由 e2e 钉：`home.feature` / `markmap.feature` / `erd.feature` / `diff.feature` / `iframe.feature` /
`viewer.feature` / `redoc.feature` / `stoplight.feature` / `scalar.feature` / `asyncapi.feature` /
`frame-precedence.feature` / `sidebar-badge.feature` /
`component-page.feature` / `packages.feature`。
`theme-copy-button` 那颗按钮的浏览器侧行为由 `copy-button.test.mts` 在 jsdom 里钉，
「点一下真的把地址放进系统剪贴板」仍要浏览器给权限，没有用例覆盖。

红线只在带覆盖率的这一步拦：`pnpm test:coverage`（`pnpm verify` 与 CI 的 verify 作业含它），
本地只跑 `pnpm test` 是量不到的。

`pnpm test:e2e` **不**计入这份覆盖率（它跑的是构建产物，没有插桩，跨 iframe 那份文档也要另收），
它钉的是真浏览器那条通路：跨文档异步投递、渲染器认不认地址里那一段、样式表与文档边界。
所以「hook 的分支已经 100%」与「三条层的用例照跑」不是重复劳动，量的不是同一件事。
